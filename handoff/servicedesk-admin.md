# Service Desk — Administration page

Built on top of the existing A5/B1 Service Desk (`servicedesk/`), which was not touched
beyond what this page needed. Four tabs — Departments, Users & Roles, SLA Config, Approval
Routing — plus a mid-build scope change from the owner (25 Aug 2026) that replaced the
department-first request form with three explicit request types. Both are covered below.

## Scope change, mid-build (25 Aug 2026)

The owner moved ticket creation from "pick a department" to **three request types**:
automation request (approval required), software issue, hardware issue (both support
tickets, no approval, straight to the IT queue). Department is no longer a question on the
form — it is stamped from the requester's own token claim, which `routers/tickets.py`
already did (`requester_dept = user.department`) before this page existed, so no backend
change was needed there. What changed:

- `frontend/src/views/RequestForm.jsx` — the type selector is now three options, each
  mapping to `(kind, service_slug)`: automation → `("automation", null)`, software →
  `("support", "software")`, hardware → `("support", "hardware")`. No new column: `service_slug`
  already existed and was unused by the requester-facing form.
- `frontend/src/components.jsx` — `requestTypeLabel()`, used by My requests, the IT console
  and the ticket detail header instead of the raw `kind` string.
- Approval Routing is explicit in the UI that it **only** governs automation requests — a
  `field-hint` line under the tab header says so, so a hardware ticket's lack of routing
  never looks like a bug.
- **The routing table is seeded, never empty.** `app/seed.py::ensure_default_approval_routing`
  runs at app startup (`app/main.py`) and inserts one catch-all `ApprovalRule`
  (department/category/priority all `NULL`) plus one `ApprovalDefault` row, both pointing at
  the seed org chart's Apex persona — only when `ORG_CHART_MODE=seed` (every demo and every
  test). It is idempotent (checked before insert) and does nothing in `http` mode, where an
  admin sets the real one. This directly satisfies "make sure the default can never be
  empty" and "one working default plus the ability to add rules is exactly right for today."

## Tables added (`app/models.py`, portable types throughout — `Uuid`, `JSON`, no Postgres-only types)

- **`departments`** — `id, name (unique), code, is_active, created_at, updated_at`. A plain
  local lookup; tickets still denormalise `requester_dept` as free text exactly as before, so
  renaming a department here does not rewrite history on existing tickets (consistent with
  how `requester_code`/`approver_code` are already denormalised elsewhere in this schema).
- **`local_roles`** — `id, sub (unique), employee_code, full_name, department, is_agent,
  is_department_manager, is_approver, created_at, updated_at`. Identity fields are a
  denormalised snapshot taken once, when a role is granted, from the read-only org-chart
  directory (`org_chart.list_known_people`) — never a second copy of the employee master to
  keep in sync. `is_agent` is informational only (see `## Assumptions`); `is_department_manager`
  and `is_approver` feed the Approval Routing tab's people pickers.
- **`sla_configs`** — `id, department_id (FK departments, CASCADE), priority, response_time_minutes,
  resolution_time_minutes, created_at, updated_at`, **unique on (department_id, priority)**.
  Ported from MiniHelp's `server/api/sla.php` with one deliberate change: priority values are
  Service Desk's own (`low|normal|high|urgent`), not MiniHelp's literal
  `low|medium|high|critical` — otherwise a config row could never match a real ticket's
  `normal`/`urgent` priority at all. Upsert on save, same as MiniHelp's `ON DUPLICATE KEY UPDATE`.
- **`approval_rules`** — `id, name, department, category, priority, approvers (JSON list of
  {sub, employee_code}), mode (sequence|any_of), is_active, created_at, updated_at`.
  `department` matches `Ticket.requester_dept`; `category` matches `Ticket.service_slug`
  ("request type/category" in the brief — read as service/system, since `kind` is always
  `"automation"` for any ticket that has an approver at all); `priority` matches
  `Ticket.priority`. Any axis may be `NULL` ("matches any"); precedence is "most axes pinned
  down wins", ties broken by creation order.
- **`approval_default`** — `id, sub, employee_code, updated_at`. Single row, upserted. Used
  only when no rule matches *and* the manager chain (`org_chart.compute_approver`) raises
  `NoApproverFound`.

**Migration**: `servicedesk/alembic/versions/fa74c3024f58_admin_departments_roles_sla_approval_.py`,
autogenerated against the portable models and reviewed by eye. `alembic upgrade head` run
clean against a fresh SQLite db during this build.

## New modules

- **`app/sla.py`** — `sla_status(cfg, created_at, first_response_at, closed_at, now)`, the
  pure calculation (tested directly against contrived timestamps), and `sla_status_for(db,
  ticket)`, the DB-backed wrapper that joins `SlaConfig` to `Department` by name. Breach is
  "exceeds", read literally: elapsed **strictly greater than** target is a breach; elapsed
  exactly equal to target is not.
- **`app/routing.py`** — `resolve_approver(db, department, category, priority,
  requester_sub)`: explicit rule (most specific first, self-approval-safe — skips a listed
  approver who is the requester and tries the next name) → manager chain
  (`org_chart.compute_approver`) → `ApprovalDefault`. Never raises; returns `source: "none"`
  only when literally nothing is configured. `preview(...)` produces the plain-language
  string the tab shows ("Rule X applies: routes to any one of [MM02]." / "No rule matches.
  Falls back to the manager chain...").
- **`app/org_chart.py`** gained `list_known_people()` — enumerates `SeedOrgChartClient`'s
  fixture for the admin page's person pickers; returns `[]` in `http` mode (same contract gap
  `HttpOrgChartClient.chain_for` already flagged — no directory-listing endpoint exists yet).
- **`app/state_machine.py`** — `apply_transition` now sets `ticket.first_response_at` on the
  first transition a ticket goes through, if it is not already set. That column existed in
  the original schema but nothing ever wrote to it; SLA response-time tracking needed it
  wired up, and "the first time anyone moves the ticket at all" was the simplest honest
  reading of "first response" available without adding new endpoints.
- **`app/seed.py`** — `ensure_default_approval_routing()`, described above.

## Endpoints added (`app/routers/admin.py`, prefix `/api/admin`)

Every route — GET and write alike — requires Service Desk's own `admin` role
(`require_role("admin")`, no `platform_admin` bypass, matching the rest of this codebase).
There is no read/write split: this is an administration page, and none of the other three
views consume this router directly (SLA status is folded into ticket serialization in
`routers/tickets.py` for whoever can already see the ticket).

- `GET/POST /departments`, `PATCH /departments/{id}` — list, create, rename/deactivate.
- `GET /people` — read-only org-chart directory for pickers.
- `GET /roles`, `PUT /roles/{sub}`, `DELETE /roles/{sub}` — list, grant/update, revoke.
- `GET/PUT /sla` — list, upsert (unique on department+priority).
- `GET/POST /approval-rules`, `PATCH/DELETE /approval-rules/{id}` — CRUD.
- `GET/PUT /approval-default` — the guaranteed fallback approver.
- `POST /approval-preview` — plain-language routing preview.

`routers/tickets.py` changed: `create_ticket` now calls `routing.resolve_approver(...)`
instead of `org_chart.compute_approver(...)` directly for automation requests (support
requests, including the new software/hardware types, never touch this path). `get_ticket`
and `list_department` now attach a computed `sla` dict to `TicketOut` (added as an optional,
non-persisted field) when a matching `SlaConfig` row exists; `list_mine`/`list_queue`/
`list_approvals` were left unchanged for time — same helper, trivial to extend.

`DevSignIn.jsx` gained a fifth persona ("MM02 — P-Spoke HOD (Service Desk admin)", roles
`["admin"]`) so the page is reachable without a real MM OS Access-page grant in this sandbox.

`RequestForm.jsx` rebuilt for the three request types (see scope change above).
`TicketDetail.jsx` shows a response/resolution SLA card when `ticket.sla` is present, with a
breach pill in orange.

## Example: how the approval matrix resolves a request

Out of the box (fresh install, `ORG_CHART_MODE=seed`): one catch-all rule named "Default —
every automation request" (department/category/priority all "any"), naming Apex (`MM01`) as
approver, `any_of` mode. An automation request from the P-Spoke operator, any priority,
matches that rule (nothing more specific exists yet) and gets `approver_sub = user:apex-1`
immediately at creation — never the manager chain (which would have resolved to the P-Spoke
HOD instead, since the operator's direct supervisor is "Operational" and does not qualify).

If an admin then adds a rule — department `P-Spoke`, priority `high`, approver `MM02` (the
P-Spoke HOD) — a P-Spoke automation request at `high` priority now routes to the HOD (more
specific: 2 axes pinned vs. the catch-all's 0), while `low`/`normal`/`urgent` P-Spoke requests
and every other department's requests still fall through to the Apex catch-all. Deleting all
rules would fall back to the manager chain, and only if that raises `NoApproverFound` (e.g.
Apex requesting something with nobody above) would `ApprovalDefault` — separately configured,
currently also Apex — be used. Verified end-to-end in this build via a live `uvicorn` smoke
test: a software issue went straight to `open` with no approver; an automation request came
back `submitted` with `approver_sub: user:apex-1`; IT claimed both from the console; the
software issue was walked to `resolved` without ever touching approval; the automation
request was proposed, sent to `manager_review`, and approved by Apex, ending at `approved`.

## Assumptions

- **`is_agent` on the Users & Roles tab is informational only.** The real `agent` role that
  gates `require_role("agent")` comes from the MM OS-issued token (granted on MM OS's own
  Access page), not from this local table. Toggling it here does not grant API access — it
  is bookkeeping for the admin's own reference. `is_department_manager` and `is_approver` are
  genuinely Service-Desk-local and do real work (they populate the Approval Routing pickers).
  This is flagged rather than silently implied because it is the one checkbox on this page
  that looks like a security control and is not one.
- **SLA priority vocabulary was changed from MiniHelp's.** MiniHelp's schema comment lists
  `low|medium|high|critical`; Service Desk's tickets use `low|normal|high|urgent`. Kept the
  latter so a configured SLA row can actually match a real ticket — a deviation from "port
  the model directly," made because the literal port would never fire.
- **"Request type/category" is `service_slug`, not `kind`.** `kind` is always `"automation"`
  for any ticket with an approver at all (support tickets, including the new software/
  hardware types, never call `resolve_approver`), so the axis that actually varies across
  automation requests is which service/system they concern.
- **Multi-approver rules resolve to one primary approver in v1.** `ApprovalRule.approvers`
  and `mode` (`sequence`/`any_of`) record the intended policy and are shown in full in the
  UI, but `Ticket.approver_sub` is a single column (unchanged v1 schema) — resolution always
  names one approver today (first non-self name in the list). Real multi-step sequencing or
  any-of-multiple-decide-either-way needs an `approval_steps`-shaped schema change; out of
  scope for this build, called out rather than silently flattened.
- **Department name matching is soft-coupled.** `SlaConfig` FKs to the local `departments`
  table; matching it to a ticket goes through `Department.name == Ticket.requester_dept`
  (free text from the requester's token). If an admin names a department differently from
  what appears in MM OS's `department` claim, SLA targets silently never match that ticket's
  department. No validation added for this — flagged rather than solved, consistent with how
  `org_chart.py` already flags its own contract gaps rather than guessing at a fix.
- **`ensure_default_approval_routing` only runs in `ORG_CHART_MODE=seed`.** In `http` mode
  (real deployment) there is no seed persona to point a default at; the routing table starts
  genuinely empty there, same as everything else in this service ("Service Desk starts
  empty" — see README.md), and an admin must configure both the catch-all rule and the
  default approver before any automation request can be raised. This matches the owner's own
  timeline ("giving me the real list tomorrow") — today's seeded Apex default is a
  placeholder to be replaced, not a permanent policy, and its rule name says so.

## Not done / left for later

- SLA badges are wired into ticket detail and the department queue only; `list_mine`,
  `list_queue` and `list_approvals` don't attach `sla` yet — same `sla_status_for` helper,
  a few lines each, left for time.
- No UI affordance to reorder rules of equal specificity (ties break by creation order,
  silently). Not needed today per the owner's own instruction not to over-invest in
  precedence; worth a "priority" number column if the real rule set (arriving tomorrow) ends
  up needing more than a handful of rules.
- `LocalRole` has no bulk-import; each grant is one admin action against one person picked
  from the seed directory. Fine at MiniMines' scale; would want a CSV path if the real
  approver list is large enough to make one-by-one tedious.
- Housekeeping: this build's own local smoke-testing left `servicedesk/servicedesk_smoke.db`
  and `servicedesk/.env.smoke` deleted from the working tree — both appear to have been
  stray files already checked into the repo (not part of the application; one is a throwaway
  SQLite file, the other an empty env file) and were removed rather than restored, but flagged
  here since this agent does not touch version control and did not confirm they were meant to
  go.
