# A5 · Service Desk

## Delivered

**`servicedesk/app/`** — a standalone FastAPI service, own database, no import from
`backend/app`.

- `models.py` — `tickets`, `proposals`, `decisions`, `comments`, `events`, exactly as
  `docs/07-service-desk.md`'s schema, but with every Postgres-only type (`uuid`, `jsonb`)
  expressed as a portable SQLAlchemy type (`Uuid`, `JSON`) — runs unchanged on SQLite here
  and Postgres in production. See `## Deviations`.
- `state_machine.py` — both state machines as transition tables (`SUPPORT_TRANSITIONS`,
  `AUTOMATION_TRANSITIONS`), `apply_transition()` the single place that validates a move,
  writes the append-only `events` row, and raises `409 invalid_transition` naming the
  current and attempted state.
- `org_chart.py` — `compute_approver()`: walks the requester-first chain, skips the
  requester even when they qualify, keeps climbing until someone else qualifies. One loop
  satisfies both "walk until a qualifying approval_level is found" and "a requester can
  never approve their own request — it escalates one level." `OrgChartClient` is a seam
  (`SeedOrgChartClient` fixture / `HttpOrgChartClient` for a lookup endpoint that does not
  exist yet — see `## Contract objections`).
- `privacy.py` — `can_see_full()`, the one place the department-queue privacy rule is
  decided; every router calls through it. `TicketOut` / `TicketHiddenOut` in `schemas.py`
  are separate Pydantic models with no shared base carrying `title`/`body`, so a hidden row
  has nothing for a network-tab inspection to find.
- `routers/{tickets,proposals,decisions,comments,mmos}.py` — the REST surface: create
  ticket, mine/department/queue/approvals list views, detail, transition, assign, comments
  (`is_internal`), proposals (versioned, `alternatives` required), decisions (immutable
  `snapshot`), `/_mmos/health`, `/api/badge`, plus `/_dev/token` (manual-testing only, 404s
  outside `AUTH_MODE=stub`).
- `mmos_seam.py`, `notifications.py`, `refs.py` — the auth seam, the four email
  notifications in one templated module (failures queued, never fail the transition), and
  `SD-YYYY-NNNN` / `AR-YYYY-NNNN` ref numbering.
- `alembic/versions/b8316dd51efa_initial.py` — autogenerated from the portable models,
  reviewed; matches `docs/07`'s columns/constraints/indexes exactly.
- `seed.py` — schema-ensure only; there is no fixture data to seed (see file).

**`servicedesk/frontend/`** — Vite + React (JS, no TypeScript — kept the dependency list to
`react`, `react-dom`, `vite`, `@vitejs/plugin-react`; no router package, a four-state switch
in `App.jsx` instead).

- `src/App.jsx` — top nav (direction B, locked in `brand/UI-DECISIONS.md`), tabs for the
  four views gated on role, avatar chip, sign-out.
- `src/views/{MyRequests,DepartmentQueue,AgentConsole,ApproverDecisions,RequestForm,TicketDetail}.jsx`
  — the four views plus the one request form and the detail page (thread, proposal,
  approval state, event timeline).
- `src/DevSignIn.jsx` — stands in for the real MM OS handoff, which needs
  `packages/mmos-client-py` wired into `app/main.py` (not done — see `## Assumptions`).
- `src/tokens.css` — the same petrol/navy/orange/cyan/Roboto tokens as
  `demo/console-directions.html`, trimmed to what this frontend uses. Orange only on
  action/attention (Approve button, private-request pill, primary CTA); no marketing copy
  anywhere in any view.
- `npm run build` passes (`frontend/dist`, ~162 KB JS + 5.6 KB CSS); `app/main.py` mounts it
  at `/` exactly the way `backend/app/main.py` mounts the MM OS shell.

**`servicedesk/README.md`** — run/migrate/seed, the manual-verification `/_dev/token` route,
both state diagrams copied in, and how `npm run build`'s output gets served.

**Tests** — `servicedesk/tests/`, 31 passing, own harness (`conftest.py`, not shared with
`backend/tests/conftest.py`). Covers: both state machines including the 409 and the 7-day
reopen window; approver escalation (operator → HOD, HOD-raises-own-request escalates past
self to Apex, Apex-with-nobody-above raises, `is_approver` override); proposal
`alternatives` required (422); decision snapshot immutable across a later proposal revision;
self-approval blocked even on a manually corrupted row; the full acceptance chain
(operator → it_review → proposal → manager_review → approved → in_build → deployed →
closed) with the exact events-row sequence asserted; the private-row rule proven from a
*third department member's* actual API response (no `title`/`body` keys at all, `hidden:
true`, comments `[]`, still counted in the queue); the auth seam's 401/403 shapes and the
deny-list; the badge endpoint; a live smoke test against a running `uvicorn` process
(create-ticket round trip, ref numbering, static frontend served) confirming the TestClient
suite matches real server behaviour.

## Deviations

- **Automation tickets never persist a `draft` row.** `POST /api/tickets` for `kind:
  "automation"` creates the row already `submitted`, with the approver computed
  immediately — matching `docs/07`'s schema comment `approver_sub -- computed at submit
  time` literally. `draft → submitted` is still a defined (unused) transition in the table
  for anyone building a save-draft feature later.
- **Two branch points in the automation ASCII diagram are genuinely ambiguous** and were
  resolved as a judgement call, not a re-specification — full reasoning in
  `app/state_machine.py`'s module docstring:
  - `changes_requested` loops back to `it_review` (so IT revises with a new proposal
    version), not to `proposal_ready`.
  - `manager_review` has three *direct* outcomes — `approved`, `changes_requested`,
    `rejected` (manager: not funded) — rather than `rejected` hanging off
    `changes_requested`.
- **`it_review → proposal_ready` and every `manager_review → *` decision are not reachable
  through the generic `POST /tickets/{id}/transition` endpoint**, only through
  `POST /proposals` and `POST /decisions` respectively (`routers/tickets.py`'s
  `GENERIC_ALLOWED` deliberately excludes them). This is what makes "a proposal gates it,
  a decision snapshots it" actually true rather than bypassable by calling the generic
  endpoint with the right `to_status`.
- **Qualifying `approval_level`** is read as "truthy and not literally `'Operational'`"
  (`org_chart.qualifies()`), inferred from `docs/02-data-model.md`'s schema comment listing
  `"L3 (HOD)"`, `"L5 (Apex)"`, `"Operational"` as the three example values — `docs/07` never
  states the exact rule. Flagged here since it's an inference, not a quote.
- **Admin sees every ticket, private or not** (`privacy.py`'s `can_see_full`) — not one of
  the literal three names in `docs/07`'s privacy rule, but the roles table gives `admin`
  "reassignment, reopen closed tickets," which is hard to do blind. An **unclaimed** private
  ticket is also visible to any `agent` (not just the eventual assignee), because otherwise
  a private automation request could never be triaged into `it_review` at all — once
  claimed, the strict three-person rule applies to every other agent. The acceptance test
  ("what a third department member actually receives") uses a plain `requester`-role peer,
  so this carve-out doesn't weaken what was asked to be proven.

## Contract objections

- **No endpoint exists for a service to walk another user's manager chain.**
  `docs/03-api-contract.md` and `docs/05-service-integration.md` give Service Desk no way to
  compute an approver: `GET /api/admin/employees` requires `is_platform_admin`, which a
  service identity should not be granted just for this. `org_chart.py`'s
  `HttpOrgChartClient` calls an assumed `GET /api/org/chain?sub=...` (service-key
  authenticated, like the heartbeat/revocation calls) that **does not exist** and is
  untested against anything real. Every test in this repo runs against
  `SeedOrgChartClient` instead. This blocks Service Desk from computing a real approver in
  production until either that endpoint is built or an equivalent is agreed. This was called
  out as a live possibility in the brief itself ("if MM OS does not expose what you need,
  note it in the handoff rather than duplicating the org chart in your database") — it
  happened.
- **Notifying anyone other than the actor by email has the same gap.** `docs/07`'s `tickets`
  schema has no `requester_email` column (by design — only `requester_code`/`requester_dept`
  are denormalised). Resolving *whose* email to notify when the actor and the requester
  differ (IT resolves a ticket, a manager decides) goes through the same `get_person()` call
  as approver computation, so it has the identical dependency on the org-chain endpoint that
  does not exist yet. `notifications.py`'s sends are therefore unverified beyond
  `smtplib.SMTP` being called correctly — there is no SMTP server in this sandbox either.

## Assumptions

**This section changed after A4 finished `packages/mmos-client-py` partway through this
build. What follows is the state as landed, read from `handoff/a4-integration.md`, compared
against what `servicedesk/app/mmos_seam.py` actually assumed and built. B1 has real
reconciliation work here — this is not a drop-in swap.**

What I assumed and built, before A4's kit existed to read:
- A free function `require_role(role)` returning a FastAPI dependency, and a `CurrentUser`
  with fields `sub, employee_code, name, email, department, division, band, approval_level,
  roles, platform_admin` (mirroring `docs/03`'s token claims 1:1). This part matches A4's
  actual `mmos_client.core` surface closely.
- My own `get_current_user` free function (no `MMOS` instance) reading a bearer token or a
  cookie I named `servicedesk_session`, verified with my own two-part HMAC "stub token"
  format (`base64url(json).hex_hmac`) gated by `AUTH_MODE=stub` — used by every test in this
  repo — with an `AUTH_MODE=http` path that does real RS256/JWKS verification but is never
  exercised.
- My own `POST /_mmos/accept` taking `{"token": "..."}` directly and setting that cookie.

What A4 actually shipped, and where it diverges:
- **The cookie is `{slug}_mmos_at`** (`servicedesk_mmos_at`), not `servicedesk_session`.
- **The handoff is two calls, not one**: `GET /_mmos/accept` serves client-side JS that reads
  the fragment and POSTs to **`POST /_mmos/session`** (not `/_mmos/accept`), which verifies
  and sets the cookie. My router has no `/_mmos/session` route at all.
- **`require_role` / `llm_guard` / `report_usage` resolve against the most-recently-
  constructed `MMOS()` instance** — so wiring this in for real means constructing one
  `MMOS(slug="servicedesk", os_url=..., service_key=..., public_paths=[...])` and calling
  `.install(app)` in `app/main.py`, which I never added (`main.py` has no `MMOS` import at
  all right now). `public_paths` would need to list `/_mmos/health`, `/api/badge`, the
  frontend's static assets, and (dev-only) `/_dev/token`.
- **`install()` flattens `HTTPException.detail`** to the top level
  (`{"error":"role_required",...}`, not `{"detail":{"error":...}}`). Every error shape in
  this repo — mine (`invalid_transition`, `not_the_approver`, `role_required` in
  `mmos_seam.require_role`, `private_ticket`, `cannot_approve_own_request`) and every test
  asserting on `r.json()["detail"]["error"]` — uses FastAPI's default nested envelope.
  Swapping to the real library means either registering the same flattening handler for
  Service Desk's own exceptions too (for one consistent envelope) or leaving the two shapes
  to coexist, and updating every test's assertion path either way.
- **`require_role` does not bypass for `platform_admin`** in A4's implementation.
  `privacy.py`'s `can_see_full()` and `routers/tickets.py`'s `_is_agent()` in this repo both
  give `platform_admin` an automatic bypass of Service Desk's own role checks — a
  deliberate-at-the-time choice that A4's landed design treats as the wrong layer (a
  service's roles are its own vocabulary, not MM OS's). Worth a explicit decision, not a
  silent inheritance either way.
- **`public_paths` prefix-matches**, not exact-matches — relevant to the `public_paths` list
  above; a bare `/api/badge` entry is enough, no trailing-segment enumeration needed.
- The org-chain lookup gap (`## Contract objections`) is untouched by A4's kit — it solves
  authentication, not the org-chart walk, which is a Service Desk-specific need with no
  parallel in the identity/tokens contract.

None of this was guessed silently: it's flagged here precisely so B1 can decide whether to
gut `mmos_seam.py` and rewire `main.py`/`routers/mmos.py` onto the real `MMOS()` instance
(the right long-term move) or keep the seam as an intentionally-thin compatibility shim.
Either way, `app/privacy.py`, `app/org_chart.py`, `app/state_machine.py` and every router's
*business* logic (as opposed to *how a request gets authenticated*) do not need to change —
they consume a `CurrentUser`-shaped object and nothing more.

## Not done

- **Real auth is not wired in.** `AUTH_MODE=http`'s RS256/JWKS path in `mmos_seam.py` is
  written but has never run against a real MM OS instance or a real signed token — there is
  neither in this sandbox. Every test and the manual smoke test both ran on `AUTH_MODE=stub`.
- **The org-chain lookup and the by-sub email lookup are both unimplemented in production
  mode** (`## Contract objections`) — `HttpOrgChartClient` is written but untested against
  anything real, since the endpoint it calls does not exist.
- **Notifications are unverified against a real SMTP server** — no server reachable in this
  sandbox; `notifications.py`'s failure-queue path (`_failed`, `retry_failed()`) is
  exercised only by construction, not by a real send failing.
- **The heartbeat loop is written but never beats** — it's a no-op whenever
  `MMOS_SERVICE_KEY` is unset (true for every test and the manual run), by design so no test
  makes a network call. Never proven against a live MM OS.
- **No Postgres run.** Per the sprint amendments, there is no Postgres on this machine.
  `alembic/versions/b8316dd51efa_initial.py` was generated against SQLite and reviewed by
  eye for Postgres-correctness (types, constraints, FKs, indexes all read as portable) but
  `alembic upgrade head` against a real Postgres `servicedesk` database has not been run.
- **Ref-number allocation is not race-proof** — `refs.next_ref()` counts existing rows with
  a `LIKE` query, no DB sequence or advisory lock. Fine at MiniMines' scale (~74 people, a
  handful of tickets a day); would need a sequence under real concurrent load.
- **The reopen-window ASCII arrow in `docs/07`'s diagram was resolved as
  `closed → resolved`, literally as drawn**, not `closed → in_progress` (which would also be
  a defensible real-world reading) — see `app/state_machine.py`'s docstring and
  `README.md`. Flagging again here because it's the one deviation most likely to be "wrong"
  rather than merely "a judgement call."

## How to verify

```bash
cd servicedesk
../backend/.venv/Scripts/python.exe -m pytest -q
# 31 passed

cd frontend && npm install && npm run build
# builds frontend/dist — this is the frontend's pass/fail gate
```

Manual, end to end, without any real MM OS:

```bash
cd servicedesk
DATABASE_URL="sqlite:///servicedesk_smoke.db" AUTH_MODE=stub ORG_CHART_MODE=seed \
  NOTIFICATIONS_ENABLED=false MMOS_SERVICE_KEY= \
  ../backend/.venv/Scripts/python.exe -m uvicorn app.main:app --port 8010 --app-dir .

curl -s http://127.0.0.1:8010/healthz
curl -s http://127.0.0.1:8010/_mmos/health
curl -s -X POST http://127.0.0.1:8010/_dev/token -H 'Content-Type: application/json' \
     -d '{"persona":"operator"}'
# use the returned token as `Authorization: Bearer <token>` against /api/tickets, etc.
```

All of the above was run during this build: pytest (31 passed), `npm run build` (succeeded),
and the manual sequence — including a real `POST /api/tickets` round trip producing
`SD-2026-0001` and the built frontend's `index.html` served from `/` by the same `uvicorn`
process.
